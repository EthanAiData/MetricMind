# ADS 指标体系梳理

> 梳理范围：本目录下 20 个 ADS SQL 文件。指标定义以 SQL 实际表达式为准；SQL 注释描述的是业务意图，两者不一致时在“口径核查”中标出。
>
> 统计日期通常由 `${pdate}` 提供。常见窗口为近 1/7/30 天；个别分析使用 7/30/90 天或固定历史区间。SQL 多数采用“保留 ADS 历史数据并 `UNION` 当日结果”的写法，另有直接插入的脚本，详见各文件。

## 1. 指标版图

| 主题 | ADS 表 / SQL 文件 | 统计粒度 | 指标范围 |
|---|---|---|---|
| 交易总览 | `ads_trade_stats` | 统计日 × 1/7/30 天 | 订单金额、订单数、下单用户数、退单数、退单用户数 |
| 品类交易 | `ads_trade_stats_by_cate` | 统计日 × 周期 × 一级/二级/三级类目 | 订单数、下单用户数、退单数、退单用户数 |
| 品牌交易 | `ads_trade_stats_by_tm` | 统计日 × 周期 × 品牌 | 订单数、下单用户数、退单数、退单用户数 |
| 品牌 × 品类 | `ads_trade_stats_by_tm_category` | 统计日 × 7/30 天 × 品牌 × 一级类目 | 订单数、用户数、商品种类数、金额、金额占比、SKU 覆盖率、环比/同比、增长类型 |
| 省份交易 | `ads_order_by_province` | 统计日 × 1/7/30 天 × 省份 | 订单数、订单金额 |

| 品牌复购 | `ads_repeat_purchase_by_tm` | 统计日 × 7/30 天 × 品牌 | 品牌复购率 |
| 新增交易用户 | `ads_new_buyer_stats` | 统计日 × 1/7/30 天 | 首次下单用户数、首次支付用户数 |
| 用户增长活跃 | `ads_user_stats` | 统计日 × 1/7/30 天 | 字段名为新增用户数、活跃用户数；当前 SQL 计算与字段名疑似错位 |
| 用户变动 | `ads_user_change` | 统计日 | 流失用户数、回流用户数 |

| 用户价值 | `ads_user_value_analysis` | 统计日 × 用户 | 累计交易/登录属性、客单价、购买周期、LTV、RFM、价值/活跃/生命周期分层、偏好、趋势 |
| 渠道流量 | `ads_traffic_stats_by_channel` | 统计日 × 1/7/30 天 × 渠道 | UV、平均会话时长、平均浏览页数、会话数、跳出率 |
| 页面路径 | `ads_page_path` | 统计日 × 1/7/30 天 × 页面路径边 | 页面访问路径次数 |
| 购物车商品排行 | `ads_sku_cart_num_top10_by_cate` | 统计日 × 三级类目 × SKU | 购物车商品数量、类目内排名（SQL 实际取 Top 3） |
| 商品关联 | `ads_sku_association_analysis` | 统计日 × 7/30/90 天 × SKU 对 | 共购次数/用户数、支持度、置信度、提升度、推荐分 |
| 活动效果 | `ads_activity_stats` | 统计日 × 活动 | 活动补贴率 |
| 优惠券效果 | `ads_coupon_stats` | 统计日 × 优惠券 | 优惠券补贴率 |

## 2. 交易与销售指标

### 2.1 交易总览、品类和品牌

| 指标 | SQL 口径 | 窗口与来源 |
|---|---|---|
| `order_total_amount` | 订单金额汇总 | 1 天取用户订单 1 日汇总；7/30 天汇总用户订单 ND 表金额字段。`ads_trade_stats` |
| `order_count` | 订单数汇总 | 同上；按订单用户汇总表中的订单数相加。总览表、品类表、品牌表 |
| `order_user_count` | 下单用户数 | 1 天统计有记录/去重用户；7/30 天统计周期内订单数大于 0 的用户。品类和品牌按维度去重 |
| `order_refund_count` | 退单数汇总 | 1 天取退款 1 日汇总；7/30 天汇总退款 ND 指标 |
| `order_refund_user_count` | 退单用户数 | 1 天按用户去重；7/30 天统计退款数大于 0 的用户 |

`ads_trade_stats` 的粒度为统计日和 1/7/30 天，没有按维度拆分。`ads_trade_stats_by_cate` 细分至三级类目，`ads_trade_stats_by_tm` 细分至品牌；两者使用订单与退单汇总做全外连接，只有一侧有数据的维度也会保留，空指标补 0。

### 2.2 品牌 × 一级类目表现

`ads_trade_stats_by_tm_category` 按最近 7 天和 30 天从订单明细计算：

- `order_count`：品牌和一级类目组合下的去重订单数。
- `order_user_count`：去重下单用户数。
- `order_sku_count`：期间内有订单的去重 SKU 数。
- `order_amount`：`split_total_amount` 求和。
- `category_amount_ratio`：该品牌类目组合金额 ÷ 同周期该一级类目总金额 × 100。
- `tm_amount_ratio`：该组合金额 ÷ 同周期该品牌总金额 × 100。
- `sku_coverage_rate`：该组合购买 SKU 数 ÷ 同周期该一级类目有销售的 SKU 数 × 100。分母是有销售 SKU，不是维表全量 SKU。
- `wow_rate`：SQL 试图比较 7 天金额与上一 7 天金额；`yoy_rate` 试图比较 30 天金额与去年同期金额；`growth_type` 按环比变化率划分高速增长（≥20%）、平稳增长（0% 至 20%）、下降（-20% 至 0%）、急剧下降（<-20%）。实际可用性见口径核查。

### 2.3 省份交易与转化

- `ads_order_by_province`：1 天直接取省份 1 日订单数、金额；7/30 天取省份 ND 指标并按省汇总。包含省份名称、区域编码和 ISO 编码。
- `ads_province_conversion_analysis.order_count`：窗口内按省份去重下单用户数；`payment_count`：窗口内按省份去重支付用户数。
- `order_to_payment_rate`：省内支付用户数 ÷ 省内下单用户数。分子和分母分别按支付回调时间、订单创建时间筛选，不保证是同一批用户的严格队列转化。
- `average_order_amount`：省内订单金额 ÷ 省内下单用户数（人均订单金额，不是每笔订单均价）。
- `user_penetration_rate`：省内支付用户数 ÷ 全国支付用户数。
- `gmv_contribution_rate`：省内订单金额 ÷ 全国订单金额。
- `wow_change_rate`：本窗口省内订单金额相对“整体窗口平移 7 天前”金额的变化率；前期金额为 0 时为 NULL。
- `regional_rank`：每个周期按省内订单金额降序的全国省份序号（`ROW_NUMBER`，并列也会排出不同序号）。
- `visitor_count`、`product_view_count`、`cart_count`、`view_to_cart_rate`、`cart_to_order_rate`、`overall_conversion_rate`：SQL 固定写 0，注释说明当前无法按省关联流量/加购数据。

### 2.4 复购、新客与营销补贴

- `ads_repeat_purchase_by_tm.order_repeat_rate`：品牌内窗口购买次数 ≥2 的用户数 ÷ 购买次数 ≥1 的用户数；窗口为 7/30 天。购买次数来自用户-SKU 订单 ND 指标先按用户和品牌汇总。
- `ads_new_buyer_stats.new_order_user_count`：按首次下单日期落入窗口的用户数；`new_payment_user_count`：按首次支付日期落入窗口的用户数，窗口为 1/7/30 天。当前 SQL 的日期边界使用固定日期，见口径核查。
- `ads_activity_stats.reduce_rate`：活动近 30 天优惠金额 ÷ 原始金额，按活动输出。
- `ads_coupon_stats.reduce_rate`：优惠券近 30 天优惠金额 ÷ 原始金额，按优惠券输出；同时保留券规则和起始日期。两个补贴率均以小数比例存储，SQL 未显式处理分母为 0。

## 3. 用户指标

### 3.1 新增、活跃、流失和留存

- `ads_user_stats`：注释意图是统计 1/7/30 天新增用户与活跃用户，但实际 SQL 中 `new_user_count` 来自登录宽表的 `login_date_last`，表现为近期最后登录用户；`active_user_count` 来自注册事实表的 `date_id`，表现为近期注册用户。需核对两列是否写反及字段定义，详见口径核查。
- `ads_user_change.user_churn_count`：当前分区中最后登录日期恰为统计日 7 天前的用户数。
- `ads_user_change.user_back_count`：同时出现在当日和前一日用户登录快照中，且最后登录日期间隔 ≥8 天的用户数。
- `ads_user_retention`：取统计日前 7 天内注册、排除统计日当天的用户，按注册日期成组。`retention_count` 为最后登录日期等于统计日的人数；`new_user_count` 为连接登录宽表后该注册日批次人数；`retention_rate = retention_count / new_user_count × 100`，单位是百分数；`retention_day` 为统计日减注册日。
- `ads_new_buyer_stats` 是交易新客（首次下单/首次支付），与 `ads_user_stats` 的注册新客不是同一概念。

### 3.2 行为漏斗

`ads_user_action` 输出 1/7/30 天以下人数：

- `home_count`：访问 `home` 页的用户数。
- `good_detail_count`：访问 `good_detail` 页的用户数。
- `cart_count`：发生加购的用户数。
- `order_count`：下单用户数。
- `payment_count`：支付用户数。

指标分别来自流量访客页表、加购/订单/支付用户汇总表。SQL 只产出阶段人数，没有产出阶段转化率，也没有把阶段用户限制为前一阶段用户的子集；因此这些数适合作为并列规模指标，不能直接当作严格的逐步漏斗转化率。

### 3.3 用户价值画像

`ads_user_value_analysis` 为用户粒度，以交易 TD 和登录 TD 宽表为基础；主要指标如下：

| 指标 | SQL 口径 |
|---|---|
| `order_count_td` / `order_amount_td` | 用户累计订单次数、累计金额（SQL 对 TD 快照字段再次按用户求和） |
| `average_order_amount` | 累计金额 ÷ 累计订单次数；订单数为 0 时写 0 |
| `purchase_cycle_days` | （最近下单日 - 首次下单日）÷（订单数 - 1）；订单数 ≤1 时 NULL |
| `account_days` | 当前日期减 SQL 中设定的注册日期；当前注册日期写死为 2020-01-01 |
| `life_time_value` | 客单价 ×（订单数 ×365 ÷ 账号存续天数）×3 年；条件不满足写 0 |
| `recency_score` | 距最近购买 ≤30/60/90/180 天分别为 5/4/3/2 分，否则 1 分 |
| `frequency_score` | 累计订单数 ≥20/10/5/2 次分别为 5/4/3/2 分，否则 1 分 |
| `monetary_score` | 累计金额 ≥10000/5000/2000/500 分别为 5/4/3/2 分，否则 1 分 |
| `rfm_score` | R、F、M 三项分数相加，范围 3–15 |
| `user_value_level` | 总分 ≥13 高价值；≥10 中高价值；≥7 中价值；≥4 低价值；否则流失风险 |
| `active_status` | 最近购买 ≤30 天或最近登录 ≤7 天为活跃；最近购买 ≤90 天或最近登录 ≤30 天为沉默；否则流失 |
| `life_cycle_status` | 按 SQL 顺序判断新用户、成长期、成熟期、衰退期、回流；当前实现的回流依赖前次订单日期，疑似无法触发 |
| `shopping_preference` | 按 F/M 分数组合分为高频低额、低频高额、高频高额、低频低额 |
| `growth_trend` | 当前 RFM 总分与 30 天前 ADS 快照分数比较，得到上升/下降/稳定 |

## 4. 流量与页面指标

- `ads_traffic_stats_by_channel` 按渠道和 1/7/30 天统计：`uv_count` = 去重 `mid_id`；`avg_duration_sec` = 平均 `during_time_1d` 毫秒 ÷1000 后取整；`avg_page_count` = 平均单会话页面数后取整；`sv_count` = 会话行数；`bounce_rate` = 页面数为 1 的会话数 ÷ 会话数，存为 0–1 小数。
- `ads_page_path` 对页面访问按 `mid_id`、自然日、周期分区，并按 `view_time` 排序，以 `LEAD` 形成相邻访问边；`source`/`target` 带 `step-N:page_id` 序号；每条边的出现次数为 `path_count`。末页没有后续页面，目标写成 `null` 字符串。

## 5. 商品分析指标

- `ads_sku_cart_num_top10_by_cate.cart_num`：全量购物车表中按 SKU 汇总 `sku_num`；按一级、二级、三级类目分区，以购物车数量降序排名。字段/表名写 Top10，但 SQL 条件 `rk<=3`，实际保留每个三级类目的前三名；使用 `RANK`，并列可能超过 3 行。
- `ads_sku_association_analysis` 在 7/30/90 天窗口中，从订单明细按同一订单生成 SKU 对：
  - `co_purchase_count`：SKU 对连接结果行数；`co_purchase_user_count`：共购用户去重数。
  - `support` = 共购次数 ÷ 总订单数。
  - `confidence` = 共购次数 ÷ 来源 SKU 购买订单数。
  - `lift` = `confidence` ÷ 目标 SKU 购买概率。
  - `recommendation_score` = 支持度 ×0.2 + 置信度 ×0.5 + 提升度 ×0.3；只保留支持度 ≥0.001 的组合。

## 6. 销售预测指标

`ads_sales_trend_forecast` 为未来 7 天分别生成整体和一级类目预测。基准值使用去年对应日（日期减 365 天）的订单数、金额、购买用户数；趋势因子为近 30 天金额相对前一个 30 天金额的增幅；近 90 天日均销售额作为参考字段。预测值大体按“去年同期基准 ×（1 + 趋势因子 + 星期因子）”计算，用户数的星期因子乘 0.8。

- `forecast_interval_lower/upper`：预测销售额乘以预测值上下浮动比例；整体基准 ±10% 加每天 1 个百分点，品类基准 ±12% 加每天 1 个百分点。
- `confidence_level`：整体为 0.95 减预测天数百分点；品类为 0.93 减预测天数百分点。
- `seasonal_index`：1 + SQL 中的星期季节因子；`trend_coefficient` 为趋势因子；`expected_growth_rate` 为（趋势因子 + 星期因子）×100。
- `anomaly_flag`：整体趋势绝对值 >0.3 或季节因子绝对值 >0.5；品类阈值分别为 0.4、0.6。
- SQL 标注整体模型为“ARIMA+季节因子”、类目模型为“Prophet”，但实际表达式是固定规则加历史基数，未见 ARIMA/Prophet 拟合过程。

## 7. 口径核查与解释限制

以下内容直接影响指标可用性，建议在报表上线或对外解释前确认：

1. **新增交易用户日期写死**：`ads_new_buyer_stats` 用 `'2020-06-14'` 计算窗口起点，而不是 `${pdate}`。调度日期变化后，1/7/30 天新增用户口径会失真。
2. **用户新增/活跃字段疑似互换**：`ads_user_stats` 的 `new_user_count` 来自登录最近日期，`active_user_count` 来自注册事实日期；与字段名、注释所述含义不一致。
3. **省级漏斗暂为占位值**：省级分析中的访客、浏览、加购、浏览到加购、加购到下单和整体转化字段固定为 0，不能解释为真实零流量。
4. **省级周环比扫描区间不足**：订单、支付和上周数据子查询统一限制 `k1 >= pdate-30`。对 30 天窗口的前一周期比较需要覆盖到约 `pdate-37`，当前限制会截断前期数据。
5. **品牌品类环比/同比窗口不匹配**：`ads_trade_stats_by_tm_category` 只生成 7 天和 30 天两行，却用 `LAG(...,1)`、`LAG(...,52)` 取前值。7 天行的前值为默认 0；30 天行的前值是 7 天金额而非上一 30 天周期；52 行滞后也没有可用年度序列。因此环比、同比及增长类型大多为 NULL 或不符合命名含义。
6. **预测季节性关联疑似产生行数膨胀**：整体和品类 SQL 将 7 行预测日期与 7 行季节性因子直接 `CROSS JOIN`，没有按 `day_offset` 关联，可能每个预测日期组合出多条不同季节因子记录；月度因子虽计算但未用于预测。需检查预测表是否出现同一日期/维度多行。
7. **商品关联按日期分组且只生成单向 SKU 对**：共购统计的中间层保留 `k1`，最终分组也包含日级订单数/购买数，却没有输出 `k1`；一个窗口可能产生多个相同商品对结果。另外 `a.sku_id < b.sku_id` 只保留 ID 小的一方为来源 SKU，置信度不是双向推荐结果。`COUNT(*)` 也不是显式去重订单数。
8. **购物车排行名为 Top10，SQL 取 Top3**：如业务需要 Top10，需调整 `rk<=3`；并列排名会使返回行数超过 3。
9. **页面路径不是会话粒度**：路径窗口按 `mid_id + 日期` 分区，没有会话 ID；同一设备一天内多次访问可能被连成一条路径。
10. **用户价值依赖默认日期和快照逻辑**：注册日期被固定为 `2020-01-01`；`t0` 只取 `${pdate}` 单日分区，却对单日数据计算 `LAG`，无法取得历史订单日期，回流分支可能始终得不到有效前次订单日。`current_date()` 也使结果依赖实际运行日而非调度日期。
11. **补贴率需明确分母处理**：活动、优惠券 SQL 未显式防止原始金额为 0；需确认 Doris 对此数据的返回行为及下游展示格式。
12. **日常写入策略需区分**：不少脚本先 `SELECT * FROM ads表 UNION 当日数据`，语义是保留历史行并追加当前结果；另一些脚本直接插入当日计算结果。注释中的“每日全量刷新”不等同于实际 truncate/rebuild，重跑和去重策略应以目标表键及调度方式为准。

## 8. 从利润拆解到业务流程指标

### 8.1 先统一“利润”口径

电商经营分析可以分三层看，避免把 GMV、收入和利润混为一谈：

1. **成交规模**：支付订单金额（常称支付 GMV）。可以拆成 `支付订单数 × 平均支付订单金额`；支付订单数又可拆为 `有效访客数 × 访客支付转化率`。订单金额、优惠、退款的统计口径要统一。
2. **净销售额与毛利**：`净销售额 = 确认收入 - 销售折扣/补贴 - 退款及退货冲减`；`毛利 = 净销售额 - 商品销售成本`；`毛利率 = 毛利 ÷ 净销售额`。财务确认收入、税额和退货冲减的规则应作为正式口径。
3. **经营贡献与经营利润**：`贡献利润 = 毛利 - 随订单变化的履约、支付、平台佣金及可归因营销成本`；`经营利润 = 贡献利润 - 固定运营费用`。如果折扣已经冲减净销售额，就不要再把同一笔折扣重复计入费用。

因此，订单金额、销量、用户数属于利润的驱动因素或代理指标，本身并不是利润。当前 ADS SQL 主要覆盖订单金额、订单/用户量、退款、补贴率、流量及用户行为；没有看到商品成本、已结算净收入、履约成本、渠道投放花费或利润字段，暂时不能直接从这些 ADS 表算出毛利、贡献利润、ROI 或真实 LTV。

### 8.2 沿业务流程布置量化指标

| 业务环节 | 建议的核心指标与拆解 | 对应现有 ADS | 可执行的运营策略 |
|---|---|---|---|
| 获客与流量 | 渠道访客 UV、获客成本 CAC、有效访问率；付费渠道可算 `CAC=获客花费÷新增付费用户` | `ads_traffic_stats_by_channel` 有 UV、会话、跳出率、时长；缺少渠道花费和可靠的新客归因 | 按渠道利润而非点击量分预算；压低高跳出低转化来源，扩投有正贡献利润的渠道；检查流量质量和落地页匹配 |
| 浏览与商品兴趣 | 商品详情到达率、详情页退出率、详情到加购率、搜索无结果率 | `ads_user_action` 有首页和详情页人数；`ads_page_path` 有页面路径，但缺少稳定会话和页面级分母指标 | 优化入口、搜索排序、商品信息和价格展示；对高流量低加购 SKU 检查价格、评价、库存、配送承诺 |
| 加购与下单 | 加购率、加购到下单率、结账放弃率；按用户或会话定义固定分母 | `ads_user_action` 有加购/下单人数，但没有阶段转化率或同一队列关系；购物车 SKU 排行在 `ads_sku_cart_num_top10_by_cate` | 对高加购低下单商品检查运费、优惠门槛、库存和结算步骤；用购物车提醒、组合购或运费门槛测试，观察增量贡献而不是只看订单数 |
| 支付与客单 | 支付转化率、支付订单数、客单价、件单价、每单件数、支付失败率；`支付 GMV=支付订单数×客单价` | `ads_trade_stats` 有订单金额和数量；`ads_user_action` 有支付人数；省级脚本有下单/支付用户数 | 简化支付流程、改善支付成功率；通过搭配购、阶梯购、加价购提高件单数；避免为拉高客单过度补贴 |
| 商品与定价 | SKU 销量、净售价、单位毛利、毛利率、缺货率、退货率；商品贡献利润 = 净销售额 - 商品成本 - 可变履约成本 | 品牌、品类、品牌×品类交易表，购物车排行和关联分析；缺少 SKU 成本、库存、净价/退货原因 | 按“销量 × 单位贡献利润”做商品组合；高销量低毛利商品调价或降本；高毛利低销量商品改善曝光；清理长期低贡献且占用库存的商品 |
| 促销与营销 | 活动/券使用人数、核销率、让利额、增量订单、增量贡献利润、促销 ROI；`ROI=(实验组增量贡献利润-活动成本)÷活动成本`（按公司约定统一公式） | `ads_activity_stats`、`ads_coupon_stats` 只有补贴率；交易分析没有活动/券的利润增量对照 | 先明确目标用户和对照组；检查优惠是否补贴了原本会购买的人；按新增贡献利润决定续投、缩量或停止，而非按核销数或 GMV 单独决策 |
| 仓配与售后 | 每单拣配/运费/包装成本、准时履约率、取消率、退款率、退货率、退货处理成本 | 目前有总退单量/退单用户量，没有履约时效、成本和退款原因 | 按地区、仓、承运商及商品识别高成本/高退货段；修正尺码与描述、包装和配送承诺；用成本与体验的综合收益确定服务等级 |
| 复购与用户经营 | 新客成本、留存率、复购率、购买频次、用户净贡献 LTV、LTV/CAC、回本周期 | `ads_new_buyer_stats`、`ads_user_retention`、`ads_repeat_purchase_by_tm`、`ads_user_value_analysis`；当前 LTV 是固定假设估算，不是净贡献 LTV | 按用户生命周期触达：新客做首购引导，活跃客做关联推荐，高价值用户做会员权益，沉默/流失风险用户做有利润门槛的召回；用队列和对照组校验增量 |

业务漏斗建议使用相邻阶段且同一统计对象的分母，例如 `详情到加购率=发生加购的详情访客÷详情访客`、`下单支付率=支付订单数÷下单订单数`。若使用人数而不是订单数，要明确一个用户多单、跨设备和时间窗口的处理规则。现有 `ads_user_action` 的人数是阶段规模指标，不能直接相除并宣称是严格转化率。

### 8.3 常见分析维度在回答什么问题

| 分析维度 | 主要观察内容 | 常见运营动作 |
|---|---|---|
| 时间（日/周/月、节假日、活动前中后） | 趋势、季节性、异常、活动增量；对比时窗口和星期结构要一致 | 排班备货、预算节奏、活动复盘；用同期或对照组避免把自然波动当作活动效果 |
| 渠道/来源/广告计划 | 各渠道带来的有效新客、转化、CAC 和后续净贡献 | 调整投放组合、受众与落地页；按获客后的贡献利润扩缩预算 |
| 商品（类目/品牌/SKU/价格带） | 规模、毛利、退货、库存与关联购买；看出畅销、盈利和滞销差异 | 商品分层、定价、组合购、清库存、补货及详情页改进 |
| 用户（新老客、注册/首购队列、RFM、生命周期） | 获客质量、留存衰减、复购频次、用户价值和流失风险 | 分层触达、会员权益、召回和推荐；对补贴设置成本上限并验证增量 |
| 地域（省/市/区域） | 销售贡献、转化、客单、履约成本、配送时效和区域差异 | 区域投放、仓网/库存配置、配送方案和本地化选品 |
| 活动/优惠券/促销类型 | 参与、核销、折扣深度、订单结构、毛利变化及增量贡献 | 调整门槛、面额、适用商品和人群；减少无增量的普惠折扣 |
| 设备/页面/访问路径 | 页面入口、路径流失、设备体验与支付障碍 | 优化导航、搜索、页面性能和结算流程；通过实验验证改版 |
| 履约/售后（仓、承运商、退款原因） | 延迟、取消、破损、退货、售后成本的集中点 | 改善库存准确率、打包、承运商和商品说明；处理高损失根因 |
| 组织/店铺/供应商 | 经营责任单元的利润、成本和服务水平差异 | 明确预算与责任边界，复制高贡献实践，处理持续负贡献单元 |

维度的作用是定位“利润变化发生在哪里、由什么人群/商品/流程驱动”，运营策略则需要回到可控的杠杆。常用排查顺序是：先看利润和贡献利润变化，再拆净收入、销量/客单、商品毛利、折扣退款、履约与获客成本；然后按时间、渠道、商品、用户、地域逐层下钻，最后用小流量实验或对照组验证动作是否带来增量利润。

一个简洁的商品/渠道决策框架是同时看**规模、单位贡献利润和增量性**：规模高且贡献为正的对象可扩大投入；规模高但贡献低的优先查折扣、成本和退货；规模低但单位贡献好时测试增加有效曝光；规模和贡献都低时先诊断定位，仍无改善再收缩投入。不能只按 GMV 排名决定预算或下架。

### 8.4 为利润分析补齐数据

建议逐单或逐订单行补齐并统一关联键：实付/确认收入、商家与平台承担的优惠、退款及退货冲减、SKU 采购/结转成本、运费与仓配成本、支付手续费、平台佣金、营销花费、活动/优惠券归属、渠道与新老客归因、库存和售后原因。再建设订单行贡献利润、活动/渠道增量贡献、用户队列净贡献 LTV 等 ADS 指标，并与财务核对汇总金额。当前 `order_total_amount`、`split_total_amount` 等字段应先确认是否含优惠、退款、税费及未支付订单，不能直接视作净收入。
